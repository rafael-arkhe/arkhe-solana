# ADR-018: Durable Journal Implementation

## Status
Accepted

## Context
We need a durable journal to ensure execution history is reliably stored and recoverable across system restarts. The choice of the underlying database engine is critical. The two primary candidates considered were `rusqlite` (a wrapper around SQLite) and `redb` (a pure Rust embedded key-value store).

## Decision
We will use **`rusqlite` (SQLite WAL mode)** as the default engine for the durable journal, with **`redb`** as an alternative option where appropriate.

## Criteria Evaluated

1. **Durability**: SQLite (with WAL mode enabled) provides battle-tested durability and crash resilience. `redb` also offers strong durability guarantees but lacks the decades of production proving that SQLite has.
2. **Maturity**: SQLite is one of the most mature and widely deployed database engines in the world. `redb` is newer, though written entirely in safe Rust.
3. **Supply Chain**: The journal is not part of the Trusted Computing Base (TCB). Therefore, the C-dependency introduced by SQLite (via `rusqlite` or `libsqlite3-sys`) does not compromise the core security invariants of the Arkhe system, making it an acceptable supply chain risk.
4. **Cross-Compilation**: SQLite can introduce complexities when cross-compiling due to its C dependencies. `redb` is pure Rust, making it trivial to cross-compile. However, robust tooling exists for cross-compiling SQLite.
5. **Size**: `redb` has a smaller footprint compared to a full SQLite build, but the difference is acceptable for our typical deployment environments.

## Consequences
- The journal will default to `rusqlite` using WAL mode for improved write concurrency and durability.
- Build environments will need a C compiler and standard tools to compile `rusqlite`.
- `redb` remains a viable fallback if strict pure-Rust or zero-dependency constraints arise in specific deployments.
